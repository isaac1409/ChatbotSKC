Qué hacer con cada archivo

1
Eliminar archivos con credenciales reales del repo
Por qué: proyecto.env y .env.txt contienen contraseñas reales y no deben existir en el historial de Git.
# Eliminar del repositorio (pero NO del sistema local si todavía los usas) git rm --cached proyecto.env git rm --cached .env.txt # Si ya no los necesitas en local tampoco rm proyecto.env .env.txt git commit -m "chore: eliminar archivos de entorno con credenciales"
⚠ Si estos archivos ya estuvieron en un commit anterior, las credenciales están en el historial de Git. Debes rotar las contraseñas aunque elimines los archivos ahora.
2
Reemplazar .gitignore con la versión nueva
Por qué: El .gitignore original solo excluía .env exacto. Ahora excluye todos los patrones: *.env, *.env.txt, proyecto.env, carpetas de datos de Docker, logs y archivos de editores.

Descarga el archivo .gitignore generado y reemplaza el existente en tu repo. Luego:

git add .gitignore git commit -m "chore: actualizar .gitignore con exclusiones completas"
3
Agregar .env.example al repo
Por qué: Es la plantilla con valores de marcador de posición (CAMBIAR_ESTO_...) que cualquier colaborador puede copiar para crear su propio .env local sin necesitar credenciales reales. Este archivo SÍ va al repo.
git add .env.example git commit -m "chore: agregar plantilla .env.example"
4
Actualizar docker-compose.yml
Por qué: Se agregó healthcheck a postgres. El cambio crítico es que evolution-api ahora espera a que postgres esté healthy (no solo started) antes de arrancar. Esto evita errores de conexión al levantar los servicios por primera vez.
git add docker-compose.yml git commit -m "fix: healthcheck postgres en docker-compose"
1
Crear el archivo .env local desde la plantilla
Por qué: El .env real NUNCA va al repo. Solo existe en la máquina donde corre Docker. Cada entorno (dev, staging, prod) tiene su propio .env con credenciales diferentes.
cp .env.example .env nano .env
2
Rellenar con contraseñas seguras
Por qué: admin123 es trivialmente adivinable. En producción, cualquier puerto expuesto con credenciales débiles es una brecha.
Cómo generar contraseñas seguras (terminal)
# Generar una contraseña de 32 caracteres aleatoria openssl rand -base64 32 # Generar múltiples de una sola vez for i in 1 2 3; do openssl rand -base64 32; done

1
Levantar todos los servicios
# Desde la carpeta del proyecto docker compose up -d # Verificar que todos están corriendo y healthy docker compose ps
✓ Todos los servicios deben mostrar healthy antes de continuar. Si alguno falla, revisa los logs con docker compose logs [servicio]
2
Crear la base de datos de n8n
Por qué: Postgres crea automáticamente solo la BD de Evolution (evolutiondb) porque está declarada en POSTGRES_DB. La de n8n (n8ndb) hay que crearla manualmente una sola vez.
docker exec -it postgres psql -U admin CREATE DATABASE n8ndb; \q
ℹ Esto solo se hace una vez. Si el contenedor de postgres se reinicia, la base de datos persiste en el volumen postgres_data.
3
Reiniciar n8n para que detecte la BD nueva
docker compose restart n8n
1
Crear las credenciales en n8n ANTES de importar el workflow
Por qué: El workflow refactorizado referencia credenciales por ID. Si importas primero y luego creas las credenciales, los nodos quedan con referencias rotas y hay que editarlos uno a uno.

Ir a Settings → Credentials → Add Credential y crear en este orden:

#TipoNombre sugeridoDatos
1 OpenAI API OpenAi account Tu API key de OpenAI
2 Google Calendar OAuth2 Google Calendar account OAuth2 con tu cuenta de Google
3 Google Sheets OAuth2 Google Sheets account OAuth2 (puede ser la misma cuenta)
4 Postgres Postgres account Host: postgres · DB: n8ndb · User/Pass del .env
5 ★ Header Auth Evolution API — apikey Name: apikey · Value: tu AUTHENTICATION_API_KEY
★ La credencial Header Auth (#5) es la más importante del refactor. Reemplaza la API key hardcodeada. Sin ella, los 3 nodos HTTP de Evolution no funcionarán.
2
Importar el workflow
Por qué: El JSON refactorizado tiene el id original del workflow — al importar reemplaza la versión anterior sin crear duplicados.

⚠ El workflow se importa con "active": false — NO lo actives todavía. Hay pasos de configuración pendientes.

4
Configurar el webhook en Evolution API
Por qué: Evolution necesita saber a qué URL enviar los mensajes entrantes.
POST http://localhost:8080/webhook/set/{tu_instancia} Headers: apikey: {tu AUTHENTICATION_API_KEY} Content-Type: application/json Body: { "url": "http://n8n:5678/webhook/f39cbfe3-edfa-4cfa-929d-b8d10bf4fbd6", "webhook_by_events": false, "webhook_base64": false, "events": ["MESSAGES_UPSERT"] }
ℹ Dentro de Docker, n8n se llama n8n en la URL, no localhost. Si Evolution es externo, usa la URL pública con dominio y SSL.
